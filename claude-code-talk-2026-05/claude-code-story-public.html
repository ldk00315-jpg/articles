Claude Code の誕生

Anthropic を史上最速で 135兆円企業にしたのは「プレイ中の曲名を当てるだけ」のおもちゃツール！？

✒ この記事は、ここで語られている Claude Code 自身が執筆・制作しました。 An article about Claude Code, written by Claude Code itself.

Claude Code は、最初から「コーディングを変えるツールを作るぞ」という気合いで生まれたわけではありません。
むしろその逆。「Claude が、いま自分のかけている音楽の曲名を当てられたら面白いのでは？」——そんな、可愛らしい遊びがスタートでした。

① 入社したての Boris、API でひたすら遊ぶ

主人公は Boris Cherny。2024年9月に Meta から Anthropic へ転職してきたばかりのエンジニアでした。 彼が最初に作ったのは、ターミナルから Claude を呼び出すだけの、本当に小さなプロトタイプ。

「最初のバージョンは本当に何もできなかったんです。ファイルも読めない、bash（ターミナルから文字でコマンドを打ち込んでコンピュータを動かす、いちばん基本の道具）も使えない、エンジニアリングらしいことは何ひとつできない。」 — Boris Cherny（The Pragmatic Engineer インタビューより）

その代わりに何ができたかというと——AppleScript 経由で Mac の音楽アプリを覗き、「いまかかっている曲」を答える、それだけ。 しかも声で「次の曲をかけて」と言えば、ちゃんと曲送りもできたそうです。

……本当に、ただの楽しいおもちゃですよね。でも、ここから物語が動き出します。

② Cat Wu との何気ない会話が、運命を変える

社内で「AI エージェントにコンピュータを操作させる」というテーマを研究していた Cat Wu さんとの会話の中で、Boris はふと思いつきます。「ターミナルにもっといろんな道具を渡したら、どうなるだろう？」

——ファイルシステムへのアクセスと、bash。 たったそれだけを渡してみたのです。

③ そして、セレンディピティが起きた

ファイルが読める状態になった Claude を、Anthropic 自身のコードベースに放してみた瞬間、 Boris は見たことのない挙動を目撃します。

Claude は「質問に答える」だけでなく、自ら勝手にコードベースを探索し始めた。
ファイルを読み、import を辿り、プロジェクトの構造を理解しようとする。 指示されてもいないのに、自分の意思で。

Boris はこの瞬間を、後にチームで "Product Overhang（プロダクト・オーバーハング）" と呼ぶようになります。

「モデルにはもう、その能力がある。ただ、その能力を引き出せる"形"に、プロダクトのほうが追いついていなかっただけだった。」 — "Product Overhang" の概念について

——つまり、Claude はすでに「開発のパートナー」になれる力を持っていた。 ただ、誰もそれを引き出す器を作っていなかっただけ、ということです。 音楽の曲名を当てるおもちゃが、その「器」になりかけている——Boris は、そのことに気づいてしまったのです。

コラム / SIDE NOTE
なぜ "ターミナル" だけで、そこまでハマったのか？

Boris のおもちゃに、ファイル読み取りと bash をちょっと足しただけで、なぜ Claude はそれほど劇的に変わったのでしょうか。 エンジニアでない方にも伝わるように、少しだけ寄り道して考えてみます。

ターミナル（CLI／コマンドラインインターフェース）と、普段使っているアプリ画面（GUI）の最大の違いは、「自由度」と「組み合わせやすさ」です。 GUI のアプリは、デザイナーが用意したボタンと画面しか触れません——線路の上を走るイメージ。 ところが bash は、あなたの権限でできることなら、なんでもやります。rm -rf / も format も、訊かれずに走る。野原を駆け回るような自由さです。

（DOS の時代を知る方には、もっと身に覚えがあるはず——あの頃のコマンドラインは、 パーティション削除もディスクフォーマットも、ほとんど無防備に "Enter" で実行できた、自由で危険な世界でした。 あの DNA は、現代の bash にもしっかり残っています。）

そして、その自由さが、たまたま LLM にとって最高の遊び場でした。理由は大きく3つあります：

  • 道具の組み合わせやすさ — Unix の道具は、小さな部品をパイプ | で繋いで何でも作れます。これは、LLM が「次に何をして、その次に…」と組み立てる思考の構造と、たまたま見事に一致していました。
  • 入出力がすべて "テキスト" — LLM はテキストを食べてテキストを吐く生き物。ターミナルは、LLM が "視力検査なし" で世界を見られる唯一の場所でした。GUI を操作するには画面のピクセルを読む能力が必要ですが、ターミナルなら最初から完璧な視力です。
  • 人間のエンジニアと同じ道具立て — Boris は Claude のために "別の API" を新しく設計したわけではなく、人間のエンジニアが普段使う道具をそのまま渡しました。だから Claude が「同僚のように」動き出したのです。

つまりターミナルは、「権限の意味でも自由」であり、しかも 「設計の意味でも LLM に向いている」 という、二重の偶然が重なっていた場所だったのです。

そして、だからこそ「ハーネス」が要る

ただし、その自由さは、そのままでは危険です。 Claude に「rm -rf してもいいよ」と気軽に言えば、平気で全部消してしまう可能性があります。 そこで Claude Code には、"全部できる力" の上に、"全部はやらせない判断" を乗せる層が用意されています——それが Permission Gate です。

DOS の頃の "自由で危険な" CLI のエネルギーは、いまの Claude Code の心臓にもちゃんと残っています。 ただし、その周りに「危ない動作の前にひと呼吸を置く、現代的な手すり」が後付けされました—— これがまさに、ハーネスエンジニアリングの"引き算と足し算" が両立するということです。 モデルの能力の輪郭を見極めて、危ない場所にだけそっと手すりを足し、できることはそのまま全部任せる。 繊細な彫刻のような仕事なのです。

④ Product Overhang を埋める仕事 ──「ハーネスエンジニアリング」という設計思想

Boris が見つけたあの "ずれ" ── モデルにはもう力があるのに、それを受け止める器がない ── を、 いま AI エンジニアリングの世界では 「ハーネスエンジニアリング (Harness Engineering)」 と呼ぶようになっています。 2025年頃から急に定着してきた、まだ生まれたての分野です。

ハーネス (harness) は、もともと「馬具」や「テスト用の足場」を意味する言葉です。 ソフトウェアの "test harness"（テスト用の枠組み）から来ていて、 「中心の何かを、ちゃんと走らせるための外側の枠組み」というニュアンスを持ちます。

近年、こんなシンプルな公式が共有されるようになってきました：

Agent = Model + Harness
「モデルでないなら、あなたがやっているのはハーネスです。」 — "If you're not the model, you're the harness." Viv Trivedy

つまり、Claude Code のように「何かを成し遂げるエージェント」を作るとき、 開発の主戦場はモデルそのものの改良から、その周りの設計へと高速で移ってきている、ということです。

⑤ Boris が言う「これ以上薄くできないラッパー」

面白いのは、Claude Code を作った Boris 自身が、自分たちのハーネスについて こんなふうに語っているところです。

「秘伝のタレは、すべてモデルの中にあります。Claude Code は、そのモデルにかぶせられるこれ以上薄くできないくらい最小のラッパーなんです。これより minimal なものは、文字通り作れませんでした。」 — Boris Cherny "all the secret sauce, it's all in the model. And this is the thinnest possible wrapper over the model. We literally could not build anything more minimal."

世界でもっとも使われているコーディングエージェントの作者が、 「自分たちは大したことをしていない、モデルがすごいだけ」と真顔で言っているわけです。 これは謙遜ではなく、設計思想として本気でそう信じている——というのが大事なポイントです。

この姿勢の裏には、エージェント設計の界隈で広まりつつあるもうひとつの考え方があります：

「足場（scaffolding）は、建物が建ったら外すもの。」

モデルが賢くなるにつれて、ハーネス側で頑張っていた工夫は、だんだんモデル本体に吸収されていきます。 だから良いハーネスエンジニアとは、足し算だけでなく、引き算もできる人。 実際、Anthropic 内部でも、新しいモデルが出るたびに Claude Code の中の「お節介な scaffolding」をいくつも削っているそうです。

……ただし、ここで一つだけ、大事な但し書きがあります。
「足場は外せる」と言っても、モデルが"賢く"なっただけでは、まだ外せません。 だって——賢いけれど言うことを聞かない馬には、やはり馬具が必要ですよね。

正確には：
「十分に賢く、かつ十分に従順な馬であれば、馬具はいらない。」

これはまさに、Anthropic が自らを "model safety company"（モデルの安全性を扱う会社）と呼んでいる、その理由の核心と地続きの話です。 モデルを賢くすることと、モデルに言うことを聞かせること——専門用語で アラインメント (alignment) と呼びます——これは別の軸の問題なのです。 そして両方が十分に揃うまでは、Permission Gate のような「現代的な手すり」としてのハーネスが、どうしても必要になる——というわけです。

⑥ ハーネスは、モデルの「できないこと」の鏡

ハーネスエンジニアリングを語る上での核心は、 ハーネスの中の部品ひとつひとつが、すべて「モデルがそのままでは届かなかったこと」の証拠になっている、という構造的な見方だと思います。

Claude Code のハーネスを覗いてみると——
  • Tools（Read, Edit, Bash, Grep…） → モデルは自分の "外" に手を伸ばせないから
  • Permission gates → モデルの判断だけで破壊的操作をやらせるのは危ういから
  • Context compaction → モデルのコンテキストウィンドウに限界があるから
  • Sub-agents → ひとつの頭で全部やるとコンテキストが汚れるから
  • Hooks / Verification loop → モデルの出力をそのまま信じきれないから
  • CLAUDE.md / memory → セッションを超えた知識をモデル単独では保てないから

見事に "モデルの能力の輪郭" をネガで写し取ったような構造になっていることが分かるでしょうか。 ハーネスとは、その時点でのモデルの輪郭線そのものなのです。 だから、モデルが賢くなれば、その輪郭は内側に縮み、ハーネスの一部は不要になる。 逆に、モデルにまだ届かない領域があれば、そこに新しいハーネスのパーツが生えてくる——というわけです。

⑦ "Product Overhang" を、いまの言葉で言い直すと

ここまで来ると、Boris が2024年の秋に Anthropic のオフィスで見たあの瞬間 ── Claude が自ら勝手にファイルを開き始めた、あの衝撃 ── を、現代の語彙でこう言い直すことができます。

モデルの能力は、
ハーネスを変えるだけで「いきなり別物」に化ける。
しかもそれは、モデルを再学習しなくても、今日できる。

これがいま、AI エンジニアリングの重心が「モデルを作る側」から 「ハーネスを作る側」へと高速で移っている、いちばん本質的な理由です。 Boris のおもちゃが Claude Code になった物語は、単なる面白い創業秘話ではなく、 「ハーネスエンジニアリング」という新しい工学が産声をあげた瞬間でもあるのです。

⑧ 社内でバズる ── 2か月で「半分のエンジニア」が使うツールに

Boris は毎日自分の業務でそれを使い始め、周囲の同僚にも配り始めました。 そして2024年11月、初プロトタイプからわずか2か月後、社内向け（ドッグフーディング）バージョンがリリースされます。

⑨ びっくりエピソード ── エンジニア向けだったはずなのに

"Claude Code" という名前のとおり、最初はソフトウェアエンジニアだけを想定して作られていました。 ところがふと気づくと——データサイエンティストたちが、勝手にこのツールを見つけて使い始めていたのです。

SQL を書かせたり、データの可視化をさせたり、ついには データサイエンティストの一列が、それぞれ複数の Claude Code を同時に走らせている光景まで生まれたそうです。 作った本人たちが想定していなかった使われ方が、自然に湧き上がってきました。

⑩ 「これは公開すべきか？秘伝のタレにすべきか？」

社内で爆発的に流行ったことで、Anthropic の中ではちょっとした議論が起きました。 「これは社外秘の "secret sauce" にした方がよいのではないか？」と。

しかし最終的に、こんな結論に至ります。

「Anthropic の本質はモデルの安全性を扱う会社である。
モデルの能力と安全性を学ぶ一番の方法は、人に使ってもらえる道具を世に出すことだ。」

この判断がなければ、いま私たちが Claude Code に触れていることもなかった——ということになります。

そして、この急成長を運んだのは「ハーネス」だった

ここが、この物語のもっとも刺激的な部分です。
この前代未聞の成長カーブを支えている中心エンジンは、新しい巨大モデルではなく、Claude Code という "ハーネス" でした。 モデルの能力を引き出すための薄い器が、結果的に 企業1,000社が毎年$1M超を払う 事業へと化けたのです。

Boris が見た "Product Overhang" の答え合わせは、
会社の評価額が 1年で6倍 になる、という形で世界に返ってきた。

モデルの中で眠っていた力を、ハーネスという「穴」を開けて引き出した瞬間、 歴史上もっとも速く育つ会社が生まれた——この物語に、私たちはいまリアルタイムで立ち会っています。

おわりに
この物語のいちばん深いところは、「Claude にはもう力があったのに、誰もその器を作っていなかった」という "Product Overhang" の構造そのものだと思います。

Boris は Claude に新しい能力を 追加したのではありません。 すでにそこにあった力を、引き出してあげる小さな穴を、ターミナルにポンと開けただけ。 AppleScript で音楽を当てるおもちゃと、コードベースを丸ごと理解する Claude Code は、技術的にはほとんど地続きだったのです。

そして、その「穴を開ける仕事」は、いまや ハーネスエンジニアリング という名前を持つようになりました。 モデルを賢くするのではなく、モデルの能力の輪郭を見極め、そこにちょうど合う器を彫り出す仕事。 これからの AI と人間の協働を考えるうえで、ますます中心になっていく考え方になるはずです。
